# راهنمای استقرار روی VPS (برای خریداران) — نسخه‌ی Turnkey

این راهنما برای کسی است که یک سرور مجازی (VPS) خریده و می‌خواهد «ابر امضاگیر» را روی دامنه‌ی خودش با **HTTPS خودکار** راه بیندازد، لایسنس را فعال کند و افزونه‌ی وردپرس را وصل کند. آشنایی با برنامه‌نویسی لازم نیست؛ فقط کپی/پیست چند دستور.

---

## ۰) پیش‌نیازها

| مورد | حداقل | توضیح |
|---|---|---|
| سیستم‌عامل | Ubuntu 22.04 / 24.04 یا Debian 12 | تمیز و تازه نصب‌شده |
| منابع | ۲ هسته CPU، ۲ گیگ RAM، ۲۰ گیگ دیسک | برای ۱۰۰ قرارداد در روز کاملاً کافی است |
| دامنه | مثلاً `sign.example.com` | رکورد **A** باید به IP سرور اشاره کند |
| ایمیل | یک ایمیل **واقعی** | برای گواهی HTTPS (Let's Encrypt). **الزامی** است؛ ایمیل‌های `@example.com` رد می‌شوند |
| پورت‌ها | ۲۲، ۸۰، ۴۴۳ باز | اسکریپت نصب فایروال را خودش تنظیم می‌کند |
| دسترسی | root یا کاربر دارای `sudo` | از طریق SSH |
| فایل‌ها | پوشه/زیپ پروژه‌ی امضاگیر | روی سرور آپلود یا `git clone` کنید |
| لایسنس | کلید `EMZ-XXXXX-…` + کلید عمومی فروشنده | از فروشنده دریافت می‌کنید |

> ⚠️ **ایران:** اگر سرور داخل ایران است و به GitHub/Docker Hub دسترسی ندارید، از میرور Docker (مثلاً `docker.arvancloud.ir`) استفاده کنید یا ایمیج‌ها را از قبل روی سرور بارگذاری کنید.
>
> **ساخت تکرارپذیر (`package-lock.json`):** ایمیج با `npm ci` از روی فایل قفل ساخته می‌شود؛ یعنی هر بار «دقیقاً» همان نسخه‌ی بسته‌ها با همان هش نصب می‌شود و ساخت روی سرور ایران با ساخت روی سیستم توسعه یکی است. اگر به `registry.npmjs.org` دسترسی ندارید، میرور npm را در `.env` بدهید: `NPM_REGISTRY=https://<آدرس-میرور>` (npm آدرس بسته‌ها را داخل lock خودکار به همان میرور تغییر می‌دهد). فایل `package-lock.json` را هرگز پاک نکنید؛ بدون آن ساخت ایمیج عمداً متوقف می‌شود.

## ۱) اتصال DNS (۵ دقیقه)

در پنل دامنه، یک رکورد بسازید:

```
نوع: A      نام: sign      مقدار: <IP سرور>      TTL: 300
```

با `ping sign.example.com` مطمئن شوید IP درست برمی‌گردد. (تا DNS درست نشود، گواهی HTTPS صادر نمی‌شود.)

## ۲) نصب با یک دستور

به سرور وصل شوید (`ssh root@IP`) و پروژه را آنجا بگذارید:

```bash
# اگر پروژه zip است:
apt-get update && apt-get install -y unzip
unzip emzagar.zip -d /opt && cd /opt/emzagar*      # یا: git clone <آدرس-مخزن> /opt/emzagar && cd /opt/emzagar

# نصب (دامنه و ایمیل «واقعی» خودتان را بنویسید؛ ایمیل الزامی است):
sudo bash scripts/install-vps.sh sign.example.com you@yourdomain.ir
```

> اگر ایمیل را ننویسید و ترمینال تعاملی باشد از شما می‌پرسد؛ در غیر این صورت نصب با پیام روشن متوقف می‌شود. دلیل: Caddy با ایمیل خالی اصلاً بالا نمی‌آید، و `docker compose` هم بدون `ACME_EMAIL` شروع نمی‌کند.

اسکریپت به‌ترتیب این کارها را می‌کند:

1. ایمیل و دامنه را اعتبارسنجی می‌کند؛
2. Docker و ابزارهای لازم (`openssl`، `curl`، `rsync`، `cron`) را (اگر نباشند) نصب می‌کند؛
3. فایروال را روی ۲۲/۸۰/۴۴۳ تنظیم می‌کند؛
4. فایل `.env` را با رمزهای تصادفی قوی می‌سازد (اگر `.env` از قبل باشد رمزها را عوض نمی‌کند؛ فقط `ACME_EMAIL` را اصلاح می‌کند)؛
5. دیتابیس، برنامه و Caddy (HTTPS خودکار Let's Encrypt) را بالا می‌آورد؛
6. منتظر می‌ماند تا سلامت برنامه تأیید شود؛
7. **بک‌آپ روزانه‌ی ساعت ۳ بامداد** (با چرخش لاگ) را زمان‌بندی می‌کند؛
8. **یک بک‌آپ آزمایشی همین حالا می‌گیرد** تا اگر زنجیره‌ی بک‌آپ مشکلی دارد همان لحظه معلوم شود، نه شب اول.

در پایان آدرس نصب و **کلید نصب** را چاپ می‌کند. زمان بار اول: ۳ تا ۸ دقیقه (ساخت ایمیج).

### نصب دستی (اگر اسکریپت را نمی‌خواهید)

```bash
cp .env.production.example .env && nano .env      # دامنه، ACME_EMAIL (الزامی)، رمزها و BACKUP_PASSPHRASE (openssl rand -hex 24)
docker compose -f docker-compose.prod.yml up -d --build
```

## ۳) راه‌اندازی اولیه

1. `https://sign.example.com/install` را باز کنید و **کلید نصب** را بدهید.
2. ایمیل و رمز **مدیر کل** را بسازید.
3. از منوی **پلتفرم ← لایسنس و به‌روزرسانی**، کلید لایسنس را وارد کنید و «فعال‌سازی» بزنید.
4. مقدار `LICENSE_PUBLIC_KEY` (که فروشنده می‌دهد) را در `.env` بگذارید تا پاسخ‌های سرور لایسنس **امضا-راستی‌آزمایی** شوند، سپس:
   ```bash
   docker compose -f docker-compose.prod.yml up -d --build
   ```
   (`--build` کلید را هنگام ساخت داخل ایمیج «تعبیه» می‌کند — ریشه‌ی اعتماد لایسنس که با تغییر `.env` بعدی قابل دستکاری نیست.)
5. (اختیاری) SMTP را در `.env` یا از «تنظیمات» پر کنید تا ایمیل بازیابی رمز و اعلان‌ها ارسال شود.

> قطع‌شدن سرور لایسنس سایت شما را **از کار نمی‌اندازد**؛ تا ۱۴ روز «مهلت آفلاین» دارید. با `LICENSE_REQUIRED=1` فقط «صدور قرارداد جدید» بدون لایسنس بسته می‌شود؛ امضای قراردادهای موجود همیشه کار می‌کند.

## ۴) اتصال وردپرس (بدون کلید و آدرس)

1. در پنل ابر: **وردپرس و ووکامرس ← دانلود افزونه** (آدرس ابر داخل فایل نوشته شده است).
2. در وردپرس: افزونه‌ها ← افزودن ← بارگذاری ← نصب ← **فعال‌سازی**.
3. خودکار به «ویزارد خوش‌آمدگویی» می‌روید (۵ قدم: کانبان، اتوماسیون، فرم‌ها، ایمنی) و اتصال برقرار می‌شود.
4. در «امضاگیر ← وضعیت سیستم» همه‌ی چراغ‌ها باید **سبز** باشند.

اگر سایت وردپرس پشت فایروال/افزونه‌ی امنیتی است، مسیر `/wp-json/emzagar/` را مجاز کنید (ابر برای تأیید دامنه و دریافت رویداد صدایش می‌زند).

## ۵) به‌روزرسانی

### الف) به‌روزرسانی ابر (روی VPS)

نسخه‌ی جدید را از فروشنده بگیرید و روی سرور اجرا کنید:

```bash
cd /opt/emzagar
bash scripts/vps-update.sh /path/to/emzagar-new.zip      # یا:  bash scripts/vps-update.sh --git
```

اسکریپت: بک‌آپ می‌گیرد ← ایمیج فعلی را برای بازگشت نگه می‌دارد ← کد را جایگزین می‌کند (`.env` و دیتا دست‌نخورده) ← می‌سازد ← تست سلامت می‌کند ← **اگر نسخه‌ی جدید بالا نیامد، خودکار به نسخه‌ی قبلی برمی‌گردد.**

> سرویس‌های Docker نمی‌توانند از داخل پنل خودشان را به‌روز کنند (پنل دلیلش را نشان می‌دهد)؛ به‌همین دلیل از این اسکریپت استفاده کنید.

### ب) به‌روزرسانی افزونه‌ی وردپرس (خودکار)

افزونه هر ۱۲ ساعت از **ابر خودتان** نسخه‌ی افزونه‌ی همراهش را می‌پرسد. پس بعد از به‌روزرسانی ابر، همه‌ی سایت‌های وردپرسی شما خودکار نسخه‌ی جدید را می‌گیرند — بدون زدن هیچ دکمه‌ای.

- «امضاگیر ← تنظیمات ← لایسنس و به‌روزرسانی»: وضعیت لایسنس، نسخه‌ی نصب‌شده/جدید و دکمه‌ی «به‌روزرسانی».
- حالت پیش‌فرض: خودکار فقط برای نسخه‌های هم‌خانواده (۲.x ← ۲.y)؛ نسخه‌ی major دستی است. قابل تغییر.
- **پیش از هر به‌روزرسانی، از قوانین/فرم‌ها/تنظیمات پشتیبان گرفته می‌شود** (تب «داده‌ها و پشتیبان» ← «بازگردانی آخرین پشتیبان»).
- بسته فقط از همان دامنه‌ی ابر شما و فقط با HTTPS پذیرفته می‌شود و ساختار آن بررسی می‌شود.

## ۶) پشتیبان‌گیری و بازیابی

### بک‌آپ شبانه

هر شب ساعت ۳ (cron) و با دستور `bash scripts/vps-backup.sh` در پوشه‌ی `backups/` (فقط برای root؛ سطح دسترسی ۷۰۰) دو فایل ساخته می‌شود:

| فایل | محتوا | فرمت |
|---|---|---|
| `db-YYYYMMDD-HHMMSS.dump` | دیتابیس PostgreSQL | `pg_dump -Fc` (custom؛ فشرده، بازیابی تراکنشی/انتخابی/موازی با `pg_restore`) |
| `storage-YYYYMMDD-HHMMSS.tar.gz.enc` | امضاها، PDFها، پیوست‌ها، **KYC و هویت**، فایل‌های Word/PDF بارگذاری‌شده (`sources`)، تصاویر لندینگ (`landing`)، لوگوها (`branding`) و `config.json` (کلید رمزنگاری) | `tar.gz` **رمزنگاری‌شده** با AES-256-CBC + PBKDF2 (۲۰۰٬۰۰۰ دور) با `openssl` |

نکته‌ها:

- **رمز بک‌آپ = `BACKUP_PASSPHRASE` در `.env`.** اسکریپت خودش آن را از `.env` می‌خواند (cron هیچ متغیر محیطی‌ای ندارد). بدون این رمز فایل `.enc` بازشدنی نیست؛ یک نسخه‌اش را **بیرون از سرور** (مثلاً مدیر رمز) نگه دارید.
- هر فایل پیش از «نهایی‌شدن» راستی‌آزمایی می‌شود (دیتابیس: `pg_restore --list`؛ storage: رمزگشایی ← gzip ← فهرست tar). فایل ناتمام هرگز با نام نهایی باقی نمی‌ماند.
- از هر نوع `BACKUP_KEEP` نسخه‌ی آخر می‌ماند (پیش‌فرض ۱۴؛ در `.env` تغییر دهید).
- **نسخه‌ی بیرونی:** `BACKUP_MIRROR=user@host:/path` (یا مسیر mount) را در `.env` بگذارید؛ با `rsync` کپی می‌شود (برای ssh کلید بدون رمز لازم است). کد خروج ۲ یعنی «بک‌آپ محلی سالم است ولی کپی بیرونی ناموفق بود». اگر `rsync` نصب نباشد همین هشدار داده می‌شود (`apt-get install -y rsync`).
- لاگ: `backups/backup.log` (هفتگی چرخانده می‌شود).
- جدا از این، خودِ برنامه هم بک‌آپ منطقی داخلی دارد (پنل «پلتفرم»، پوشه‌ی `/app/backups` روی volume جدا) با کلید بازیابی `emz-rk1-…`؛ این دو مکمل‌اند.

### بازیابی (خودکار و امن)

```bash
cd /opt/emzagar
bash scripts/vps-restore.sh                                  # آخرین نسخه‌ی db + storage (با تأیید دستی)
bash scripts/vps-restore.sh --stamp 20250101-030000 --yes    # نسخه‌ی مشخص، بدون پرسش
bash scripts/vps-restore.sh --db-only                        # فقط دیتابیس   (یا --files-only)
bash scripts/vps-restore.sh --dir /mnt/restored-backups      # پوشه‌ی دیگر (مثلاً کپی برگشتی از mirror)
```

اسکریپت: صحت و رمز فایل‌ها را «پیش از هر تغییر» می‌سنجد ← نسخه‌ی اضطراری وضعیت فعلی را می‌سازد (`backups/pre-restore-*.dump`) ← برنامه را متوقف می‌کند ← دیتابیس را در یک پایگاه **موقت** بازیابی می‌کند (`pg_restore --single-transaction`) و فقط پس از موفقیت کامل با پایگاه فعلی عوض می‌کند (خطا ⇒ داده‌ی فعلی دست‌نخورده) ← storage را با کاربر `app` باز می‌کند ← برنامه را بالا می‌آورد و سلامتش را می‌سنجد. فایل‌های قدیمی `db-*.sql.gz` و `storage-*.tar.gz` (قبل از این نسخه) هم پذیرفته می‌شوند.

### بازیابی دستی (اگر اسکریپت در دسترس نیست)

```bash
cd /opt/emzagar
DC="docker compose -f docker-compose.prod.yml"
export BACKUP_PASSPHRASE='…'          # همان مقدار .env

# ۰) سنجش فایل‌ها (باید بدون خطا تمام شود)
$DC exec -T db pg_restore --list < backups/db-XXXX.dump > /dev/null
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -pass env:BACKUP_PASSPHRASE -in backups/storage-XXXX.tar.gz.enc | gzip -dc | tar -tf - | head

# ۱) دیتابیس (در پایگاه موقت، بعد جایگزینی)
$DC stop app
$DC exec -T db psql -U emzagar -d postgres -c "CREATE DATABASE emzagar_restore;"
$DC exec -T db pg_restore -U emzagar -d emzagar_restore --no-owner --exit-on-error --single-transaction < backups/db-XXXX.dump
$DC exec -T db psql -U emzagar -d postgres -c "ALTER DATABASE emzagar RENAME TO emzagar_old;" \
                                            -c "ALTER DATABASE emzagar_restore RENAME TO emzagar;" \
                                            -c "DROP DATABASE emzagar_old WITH (FORCE);"

# ۲) فایل‌ها: «رمزگشایی ← gunzip ← tar»  (فایل .enc را مستقیم gunzip نکنید؛ رمزنگاری‌شده است)
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -pass env:BACKUP_PASSPHRASE -in backups/storage-XXXX.tar.gz.enc \
  | gzip -dc | $DC run --rm --no-deps -T app tar -C /app -xf -

$DC up -d app
```

> بک‌آپ‌های قدیمی بدون رمز (`db-*.sql.gz`، `storage-*.tar.gz`): دیتابیس با `gunzip -c فایل | $DC exec -T db psql -U emzagar -d emzagar_restore -v ON_ERROR_STOP=1 --single-transaction` و فایل‌ها با `gunzip -c فایل | $DC run --rm --no-deps -T app tar -C /app -xf -`.

## ۷) پایش و سلامت

| چه چیزی | کجا |
|---|---|
| سلامت برنامه (Docker/لود‌بالانسر) | `https://sign.example.com/api/health` |
| وضعیت تجمیعی همه‌ی سرویس‌های ابر (UptimeRobot) | `curl -H "Authorization: Bearer $CRON_SECRET" https://sign.example.com/api/health/status` |
| وضعیت هر سایت وردپرسی | «امضاگیر ← وضعیت سیستم» (چراغ سبز/زرد/قرمز) |
| پایش بیرونی هر سایت وردپرسی | آدرس توکن‌دار پایین همان صفحه (`/wp-json/emzagar/v1/health?token=…`؛ ۲۰۰ = سالم، ۵۰۳ = مشکل) |
| از خط فرمان وردپرس | `wp emzagar health` (کد خروج ۱ = مشکل جدی) |

لاگ برنامه: `docker compose -f docker-compose.prod.yml logs -f app`

**لاگ و منابع:** لاگ هر سرویس چرخشی است (۵ فایل × ۱۰ مگابایت) و دیسک را پر نمی‌کند. سقف حافظه: برنامه ۱٫۵ گیگ (`APP_MEM_LIMIT`)، دیتابیس ۱ گیگ (`DB_MEM_LIMIT`)، Caddy ۲۵۶ مگ؛ روی VPS دو گیگی مقدارهای کوچک‌تر (مثلاً `APP_MEM_LIMIT=1g`، `APP_HEAP_MB=700`، `DB_MEM_LIMIT=700m`) در `.env` بگذارید. اگر برنامه از سقف رد شود فقط همان کانتینر (با `restart` خودکار) ری‌استارت می‌شود، نه کل سرور.

## ۸) امنیت: چک‌لیست ۵ دقیقه‌ای

- [ ] ورود SSH با کلید (نه رمز)، و `PermitRootLogin prohibit-password`.
- [ ] `.env` فقط برای root خوانا باشد (اسکریپت `600` می‌گذارد) و هرگز در Git قرار نگیرد.
- [ ] `LICENSE_PUBLIC_KEY` پر شده باشد.
- [ ] `SEED_DEMO=0` و `ALLOW_DEV_OTP=0` بماند (پیش‌فرض).
- [ ] بک‌آپ بیرونی هفتگی.
- [ ] در وردپرس: «محدودیت و امنیت» را مرور کنید (سقف روزانه‌ی صدور از فرم، قفل اضطراری).
- [ ] پشت Cloudflare هستید؟ در وردپرس فیلتر `emzagar_client_ip` را برای IP واقعی بازدیدکننده تنظیم کنید.

## ۹) عیب‌یابی سریع

| نشانه | علت محتمل | راه‌حل |
|---|---|---|
| مرورگر «اتصال امن نیست» می‌دهد | DNS هنوز به سرور اشاره نمی‌کند یا پورت ۸۰/۴۴۳ بسته است | DNS و فایروال سرویس‌دهنده (Security Group) را ببینید؛ `docker compose -f docker-compose.prod.yml logs caddy` |
| `/install` بدون کلید باز نمی‌شود | `INSTALL_KEY` فعال است | مقدار آن در `.env` است |
| افزونه «در حال اتصال…» می‌ماند | ابر نمی‌تواند به `/wp-json/emzagar/v1/verify` سایت برسد | فایروال/افزونه‌ی امنیتی؛ «وضعیت سیستم ← دسترسی ابر به وردپرس» |
| چراغ Heartbeat قرمز | WP-Cron اجرا نمی‌شود | برای سایت کم‌بازدید: `*/5 * * * * curl -s https://سایت-شما/wp-cron.php` و `DISABLE_WP_CRON=true` |
| یک بخش افزونه با افزونه‌ی دیگر تداخل دارد | — | «تنظیمات ← ماژول‌ها» همان بخش را خاموش کنید (یا `wp emzagar modules disable forms`) |
| پیشخوان وردپرس باز نمی‌شود | خطای شدید | در `wp-config.php`: `define('EMZAGAR_SAFE_MODE', true);` |
| ایمیل‌ها نمی‌رسد | SMTP تنظیم نیست | `SMTP_*` را در `.env` پر کنید و `up -d` بزنید |
| `docker compose` با خطای «ACME_EMAIL» شروع نمی‌شود / Caddy بالا نمی‌آید | `ACME_EMAIL` در `.env` خالی است | یک ایمیل واقعی بگذارید (نه `@example.com`) و `up -d` بزنید |
| بک‌آپ شبانه شکست می‌خورد | `BACKUP_PASSPHRASE` در `.env` نیست، یا docker/rsync مشکل دارد | `bash scripts/vps-backup.sh` را دستی اجرا کنید؛ پیام خطا دقیق است. لاگ: `backups/backup.log` |
| ساخت ایمیج «package-lock.json not found» می‌دهد | فایل قفل پاک شده | از نسخه‌ی اصلی برگردانید (`npm install --package-lock-only`) |
| ساخت ایمیج روی سرور ایران گیر می‌کند | دسترسی به `registry.npmjs.org` | `NPM_REGISTRY=https://<میرور>` را در `.env` بگذارید |
| به‌روزرسانی ابر شکست خورد | — | خودکار برگشت می‌خورد؛ لاگ را ببینید؛ بک‌آپ شب قبل هم هست |
| «ظرفیت دامنه‌ی لایسنس پر است» | لایسنس برای تعداد مشخصی دامنه است | از فروشنده یک دامنه را آزاد کنید یا لایسنس را ارتقا دهید |

## ۱۰) حذف

```bash
cd /opt/emzagar
docker compose -f docker-compose.prod.yml down -v      # ⚠️ دیتابیس و فایل‌ها را هم پاک می‌کند! قبلش بک‌آپ بگیرید
crontab -l | grep -v vps-backup.sh | crontab -
```

حذف افزونه از وردپرس، اتصال را در ابر می‌بندد (کلید API باطل می‌شود)؛ قراردادها و قالب‌ها در حساب شما می‌ماند. **پیش از حذف، «خروجی کامل داده‌ها» را بگیرید.**
