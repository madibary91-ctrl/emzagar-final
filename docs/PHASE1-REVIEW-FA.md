# بازبینی فنی فاز ۱ — پاسخ به ۷ پرسش (امضاکننده‌ی مهمان و کتابخانه‌ی قالب‌ها)

> هر پاسخ با کد و آزمونِ خودکار پشتیبانی می‌شود. آزمون‌های موجود دست‌نخورده‌اند؛ فقط فایل‌های آزمون جدید اضافه شد.

## ۱) package-lock.json و رجیستری
- در مخزن GitHub **هیچ `package-lock.json`‌ای ردیابی نمی‌شد** (پس چیزی دستکاری نشده بود). `Dockerfile` هم برای همین حالت آماده است (با قفل‌فایل `npm ci`، بدون آن `npm install`).
- یک قفل‌فایل تازه با **رجیستری رسمی** (`https://registry.npmjs.org/`) ساخته شد: همه‌ی ~۶۲۰ بسته با `integrity`، بدون هیچ میرور/آدرس `http`.
- ضد بازگشت: `tests/unit/release-integrity.test.ts` اگر قفل‌فایل به هر آدرسی جز رجیستری رسمی اشاره کند (یا `.npmrc` رجیستری دیگری تحمیل کند) شکست می‌خورد.

## ۲) مهاجرت دیتابیس برای نصب‌های موجود
- مکانیزم: `src/db/ddl.ts` از `schema.ts` دستورهای `ALTER TABLE … ADD COLUMN IF NOT EXISTS` می‌سازد و `applySchema()` هنگام بالا آمدن برنامه (`instrumentation.ts`) آن‌ها را در **یک تراکنش + قفل مشاوره‌ای** اجرا می‌کند. خطا ⇒ rollback و (در production) توقف برنامه؛ هرگز ساختار نیمه‌کاره.
- `users.is_guest boolean NOT NULL DEFAULT false` ⇒ همه‌ی کاربران قدیمی «مهمان نیستند». `templates.library_key text NULL` ⇒ همه‌ی قالب‌های قدیمی «دست‌ساز» می‌مانند.
- **ریسک واقعی که یافت و رفع شد:** برای جلوگیری از تکرار قالب کتابخانه، ایندکس یکتای `templates(workspace_id, library_key) WHERE library_key IS NOT NULL` اضافه شد. نصب‌هایی که فاز ۱ را (بدون این ایندکس) زنده کرده‌اند ممکن بود کپی تکراری داشته باشند و ساخت ایندکس، ارتقا را متوقف می‌کرد. `PRE_INDEX_FIXES` در `applySchema` پیش از ساخت ایندکس، فقط برچسب کتابخانه‌ی کپی‌های اضافه را برمی‌دارد (قدیمی‌ترین نگه داشته می‌شود؛ **هیچ قالبی حذف نمی‌شود**).
- آزمون: `tests/integration/schema-upgrade-phase1.test.ts` — روی دیتابیس جداگانه، ساختار «پیش از فاز ۱» با داده‌ی واقعی می‌سازد، `applySchema` واقعی را اجرا می‌کند و حفظ داده، پیش‌فرض‌ها، ایدمپوتنت‌بودن و سناریوی کپی‌های تکراری را بررسی می‌کند.

## ۳) عضویت مهمان در Workspace و RBAC
- **بله، مهمان ردیف `workspace_members` دارد** با نقش `client` (تنها یک فضا). دلیل: `assertUsersInWorkspace` (ایزولاسیون مستاجر هنگام صدور قرارداد) و کلیدهای خارجی همین جدول را معیار می‌گیرند.
- شمارش تیم/سقف اعضای طرح (`getUsage`، `assertCanAddMember`) و فهرست «تیم» فقط نقش‌های غیر `client` را می‌شمارند ⇒ مهمان هیچ‌جا عضو تیم حساب نمی‌شود (آزمون دارد).
- RBAC: `getTeamContext` فقط نقش‌های تیمی را می‌پذیرد؛ مهمان هیچ نقش تیمی ندارد.
- **گاردهای جلوگیری از ورود (چندلایه):** ورود و فراموشی رمز (از فاز ۱) + **جدید:** `createSession` (آخرین خط دفاع برای همه‌ی مسیرها: رمز، 2FA، دعوت، SSO وردپرس) برای مهمان خطا می‌دهد؛ `getCurrentUser` برای مهمان حتی با کوکی معتبر `null` می‌دهد؛ مسیر SSO، `acceptInvite`، `inviteMemberAction` و `changeRoleAction` مهمان را رد می‌کنند (ارتقای دست‌ساز به نقش تیمی ممکن نیست).

## ۴) ارتقای مهمان به کاربر واقعی
- ساختار مناسب است: مهمان یک ردیف `users` است و همه‌ی جدول‌ها (`contract_signers`، `signing_links`، `audit_logs`، فیلدها، عضویت) به `users.id` ارجاع دارند. ارتقا فقط یک `UPDATE` روی همان ردیف است؛ هیچ مهاجرت/ادغام داده‌ای لازم نیست.
- اجرای آماده برای فاز ۲: `upgradeGuestToUser(userId, { email, passwordHash, verifiedMobile })` در `src/modules/guests/service.ts` — اتمی و ضدمسابقه (`FOR UPDATE` + شرط `is_guest`)، موبایل تأییدشده با OTP باید با هویت مهمان یکی باشد، ایمیلِ دارای حساب رد می‌شود (ادغام خودکار نداریم)، ایمیل تأییدنشده می‌ماند تا خط‌لوله‌ی تأیید ایمیل ثبت‌نام اعمال شود، رویداد `guest.upgraded` ثبت می‌شود.
- نکته‌ی طراحی: هویت مهمان «در هر فضای کاری» جداست؛ اگر همان فرد در دو فضا مهمان بوده، دو ردیف دارد و ارتقای یکی دیگری را تغییر نمی‌دهد (انتخاب آگاهانه برای جلوگیری از نشت بین مستاجران).

## ۵) امنیت OTP و شناسنامه‌ی دیجیتال
- لایه‌های موجود: فاصله‌ی ارسال مجدد ۱۱۷ ثانیه (دیتابیس)، سقف ۵ تلاش برای هر کد (اتمیک)، سقف ۲۰ تلاش در ۲۴ ساعت، محدودیت نرخ حافظه‌ای به‌ازای امضاکننده/لینک/IP.
- **ضعف یافت‌شده:** سقف ساعتی ارسال فقط در حافظه‌ی فرایند بود (با ری‌استارت یا چند نمونه ریست می‌شد ⇒ ریسک پیامک‌بمبارانی و هزینه). **رفع:** `OTP_MAX_SENDS_PER_HOUR = 6` در دیتابیس (`deliverSigningOtp`) برای همه‌ی مسیرها؛ رد شدن در ممیزی ثبت می‌شود.
- **IP و User-Agent:** در `audit_logs` برای `otp.sent` / `otp.failed` / `otp.verified` / `contract.signed` و در ردیف `contract_signers` (`ip`، `user_agent`، `otp_verified_at`، `mobile`) ثبت می‌شود (آزمون دارد). IP از سمت راست `X-Forwarded-For` و با `TRUSTED_PROXY_HOPS` (پیش‌فرض ۱ = یک پراکسی جلوی برنامه) خوانده می‌شود؛ برای نصب بدون پراکسی مقدار `0` بگذارید.

## ۶) معماری کتابخانه‌ی قالب‌ها
- ۳۲ قالب **داده‌ی کد** (`src/modules/library/catalog/*.ts`) و کاتالوگِ مشترک و فقط‌خواندنی‌اند؛ در دیتابیس ذخیره نمی‌شوند و Seed دیتابیسی ندارند (پس اجرای دوباره‌ی Seed چیزی تکراری نمی‌کند). هنگام «افزودن به قالب‌های من» **یک کپی مستقل برای همان فضای کاری** ساخته می‌شود (`templates.library_key`).
- **ضعف یافت‌شده:** جلوگیری از تکرار فقط «بررسی ← درج» بود؛ دو کلیک هم‌زمان کپی تکراری می‌ساخت. **رفع:** ایندکس یکتای جزئی + `ON CONFLICT DO NOTHING` + بازخوانی کپی برنده.
- آزمون: `tests/integration/library-idempotency.test.ts` (۳۲ قالب × ۲ بار، ۸ درخواست هم‌زمان، استقلال بین فضاها، رد تکرار توسط خود دیتابیس).
