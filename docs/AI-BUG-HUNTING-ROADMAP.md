## 0) چرا این روش؟ اصل‌های راهبردی

پروژه در حال حاضر حدود **۱۰۰۰ فایل**، بیش از **۶۰ ماژول** در `src/modules`، حدود **۱۳۰ مسیر (page/route)**، ۲۴ فایل اسکیمای دیتابیس در `src/db/schema/`، افزونه‌ی PHP وردپرس و دو سرویس شبیه‌ساز دارد. هوش مصنوعی نمی‌تواند همه را یک‌جا در ذهن نگه دارد. پس این اصل‌ها را رعایت می‌کنیم:

| # | اصل | معنی عملی |
|---|---|---|
| ۱ | **برش کوچک، عمق زیاد** | هر نشست فقط یک «بخش» یا حتی یک «جزء» را می‌بیند. بخش‌ها در این سند به ۱ تا ۵ فایل اصلی بریده شده‌اند. |
| ۲ | **اثبات یا حذف** | تاریخچه‌ی ممیزی‌های قبلی (`docs/GLM-AUDIT*.md`) نشان می‌دهد بخشی از ادعاهای هوش مصنوعی نادرست (False Positive) بود. بدون «فایل:خط + سناریوی بازتولید + آزمون ناموفق»، هیچ یافته‌ای پذیرفته نمی‌شود. |
| ۳ | **اول باگ‌های پول و هویت** | خطای ظاهری قابل‌تحمل است. خطا در پول، امضا، دسترسی و حریم خصوصی قابل‌تحمل نیست. موج‌ها بر اساس «هزینه‌ی خطا» چیده شده‌اند، نه بر اساس ترتیب پوشه‌ها. |
| ۴ | **هر رفع = یک آزمون** | هر باگ تأییدشده یک آزمون Vitest ناموفق می‌گیرد، بعد رفع می‌شود و آزمون سبز می‌ماند. فهرست آزمون‌ها در `tests/integration/*` و `tests/unit/*` است. |
| ۵ | **هوش مصنوعی + ابزار + انسان** | هوش مصنوعی کد را می‌خواند، ابزارها (بخش ۸) رفتار را می‌سنجند، و تست دستی (سند دوم) چیزهایی را می‌بیند که هیچ‌کدام نمی‌بینند: پیامک واقعی، بانک واقعی، گوشی واقعی. |
| ۶ | **دو بازیگر متفاوت** | یک نشست «شکارچی» باگ پیدا می‌کند. یک نشست جدا و بی‌خبر از اولی «دادستان معکوس» است و تلاش می‌کند هر یافته را رد کند (بخش ۳-ب). فقط یافته‌ای که از هر دو رد شد وارد صف رفع می‌شود. |
| ۷ | **حافظه‌ی بیرونی** | نتیجه‌ی هر نشست در «دفتر پیگیری» (بخش ۹) ثبت می‌شود تا نشست بعدی دوباره همان را نکند و هیچ بخشی جا نماند. |

### چه چیزی در حوزه‌ی این نقشه نیست
- بازنویسی، ماژولار کردن یا تغییر معماری (طبق قانون این مرحله).
- افزودن قابلیت تازه. فقط باگ و ریسک.

## 2) آماده‌سازی: پیش از اولین پرامپت

### ۲-الف) کد را برای هوش مصنوعی آماده کنید
1. آدرس مخزن: `https://github.com/madibary91-ctrl/emzagar-final`. یک **commit hash ثابت** برای کل دوره‌ی باگ‌گیری انتخاب کنید و در دفتر پیگیری بنویسید. اگر وسط کار کد عوض شود، یافته‌ها بی‌اعتبار می‌شوند.
2. در هر پرامپت **مسیر دقیق فایل‌ها** را بدهید، نه فقط نام ماژول. هر بخش در این سند فهرست «فایل‌های هدف» دارد.
3. هوش مصنوعی را وادار کنید فایل را واقعاً بخواند، نه حدس بزند. جمله‌ی کلیدی: «قبل از هر ادعا، خطوط کد را عیناً نقل کن».
4. فایل‌های بزرگ‌تر از چند صد خط را بخش‌بخش بدهید (مثلاً `src/modules/contracts/lifecycle.ts` و `src/modules/signing/*`).

### ۲-ب) محیط اجرای واقعی برای تأیید
- نصب وابستگی و ساخت دیتابیس آزمایشی: `npm ci` و سپس `npx vitest run`. دیتابیس `emz_test` خودکار ساخته می‌شود و به دیتابیس واقعی دست نمی‌زند.
- شبیه‌ساز بیرونی: `npx tsx simulator/cli.ts --port 4010` و `EXTERNAL_SIM_URL=http://127.0.0.1:4010 npm run dev` (زرین‌پال، کاوه‌نگار، ملی‌پیامک و GapGPT شبیه‌سازی می‌شوند).
- اگر هوش مصنوعی ابزار اجرا دارد، از آن بخواهید هر یافته را با **اجرای یک آزمون واقعی** تأیید کند.

### ۲-ج) قاعده‌ی نشست
- هر نشست = یک بخش (یا جزء). چند بخش را در یک نشست نریزید.
- ابتدای هر نشست «پرامپت پایه» (بخش ۳) را بچسبانید.
- پایان هر نشست: «جدول یافته‌ها» را در دفتر پیگیری ثبت کنید.

## 3) پرامپت پایه (Master Preamble)

### ۳-الف) پرامپت شکارچی (برای شروع هر نشست)

```text
نقش تو: مهندس ارشد امنیت و کیفیت نرم‌افزار. پروژه‌ی «امضاگیر» (Emzagar) را بازبینی می‌کنی؛
یک SaaS امضای آنلاین قرارداد برای بازار ایران با Next.js 16 (App Router)، PostgreSQL،
Drizzle ORM، Tailwind 4 و افزونه‌ی وردپرس (PHP).

بافت پروژه:
- کد دامنه‌ای در src/modules/<دامنه>/ است؛ اسکیمای دیتابیس در src/db/schema/*.ts؛
  SQL نصب‌کننده از اسکیما ساخته می‌شود (src/db/ddl.ts).
- تغییر وضعیت قرارداد باید در یک تراکنش و زیر قفل ردیف باشد (src/modules/contracts/lifecycle.ts)،
  و اثرهای شبکه‌ای (پیامک، ایمیل، وب‌هوک) فقط پس از commit و از طریق صف کار (src/modules/jobs).
- مبلغ‌ها تومانِ عدد صحیح‌اند و باید همیشه سمت سرور محاسبه شوند.
- متن‌ها فارسی (RTL)، تاریخ‌ها شمسی در نمایش و میلادی/UTC در ذخیره، ارقام فارسی/عربی/لاتین باید همه پذیرفته شوند.
- مدل نقش‌ها: owner / admin / member / viewer / client + مدیر کل پلتفرم + امضاکننده‌ی مهمان (بدون حساب).

قواعد سخت:
1. فقط کد را تحلیل کن؛ هیچ فایلی را تغییر نده و پیشنهاد بازنویسی یا ماژولار کردن نده.
2. هر یافته باید «فایل:شماره‌ی خط» و نقل عین کد داشته باشد. بدون آن، ننویس.
3. هر یافته باید «سناریوی بازتولید گام‌به‌گام» و «اثر واقعی بر کاربر/پول/داده» داشته باشد.
4. اگر مطمئن نیستی، آن را در بخش «مشکوک ولی اثبات‌نشده» بنویس، نه در بخش یافته‌ها.
5. قبل از ادعا بررسی کن آیا قبلاً در docs/GLM-AUDIT*.md یا tests/integration/* پوشش و رفع شده است.
   اگر شده، فقط ثابت کن رفع شکسته است؛ وگرنه ننویس.
6. هر یافته با قالب استاندارد (شناسه، شدت، دسته، فایل، توضیح، بازتولید، رفع پیشنهادی، آزمون پیشنهادی) گزارش شود.
7. در پایان: فهرست «مسیرهایی که بررسی نکردم و چرا» را بنویس تا پوشش مشخص باشد.

بخش این نشست: <شناسه و نام بخش>
فایل‌های هدف: <فهرست مسیرها>
تمرکز: <یکی از پرامپت‌های همان بخش>
```

### ۳-ب) پرامپت دادستان معکوس (نشست جدا، برای رد کردن یافته‌ها)

```text
تو بازبین مستقل هستی. فهرست زیر را یک بازبین دیگر ادعا کرده است. وظیفه‌ی تو «رد کردن» است.
برای هر یافته: کد را خودت بخوان؛ بررسی کن آیا
(الف) شرط/قفل/اعتبارسنجی دیگری در بالادست یا پایین‌دست مسیر را خنثی می‌کند،
(ب) دیتابیس (قید CHECK، ایندکس یکتا، FK) جلوی آن را می‌گیرد،
(پ) آزمونی در tests/ همین را پوشش داده،
(ت) سناریوی بازتولید در عمل ممکن است یا فقط نظری است.
خروجی هر یافته: «تأیید شد» یا «رد شد»، به‌همراه دلیل و نقل کد. «شاید» قبول نیست.
اگر تأیید می‌کنی، کوتاه‌ترین آزمون Vitest ناموفق را که باگ را اثبات می‌کند بنویس (فقط متن، بدون اعمال).
```

### ۳-پ) پرامپت «پس از رفع» (پیش از بستن یافته)
```text
رفع زیر اعمال شده است: <diff>. 
۱) آیا باگ اصلی کاملاً رفع شده؟ ۲) آیا مسیرهای هم‌خانواده (همان الگو در جاهای دیگر) هنوز باگ دارند؟ با grep فهرست کن.
۳) آیا رفع یک رگرسیون تازه ساخته (تراکنش، قفل، ترتیب، دسترسی)؟ ۴) کدام آزمون‌های موجود باید دوباره اجرا شوند؟
```

## 4) قالب استاندارد گزارش یافته و مقیاس شدت

### قالب یافته
```markdown
### <شناسه مثل S06-017>  <عنوان کوتاه>
- شدت: Critical | High | Medium | Low
- دسته: Race | Auth | Tenancy | Money | Data-loss | Leak | Validation | State-machine | UX | Perf | I18n | Ops
- فایل:خط: src/modules/...:123
- کد (نقل عین):
- بازتولید: ۱) ... ۲) ... ۳) ...
- اثر واقعی:
- رفع پیشنهادی (حداقلی):
- آزمون پیشنهادی (Vitest/Playwright):
- پیش‌شرط/احتمال: (آیا فقط با زمان‌بندی خاص یا فقط با ادمین رخ می‌دهد؟)
- خانواده: (همان الگو در کجاهای دیگر؟)
```

### مقیاس شدت
| شدت | تعریف | مثال برای این پروژه | تصمیم |
|---|---|---|---|
| **Critical** | پول گم/دوبار، امضای جعلی، نشت داده‌ی مشتری دیگر، دور زدن OTP، اجرای کد از راه دور | یک امضا قرارداد لغوشده را «امضاشده» کند؛ پرداخت دوبار فاکتور شود | لانچ ممنوع |
| **High** | قطع یک جریان اصلی، افشای اطلاعات محدود، بن‌بست داده | قرارداد در وضعیت بن‌بست بماند؛ پیامک OTP نرسد و سوخته شود | قبل از لانچ |
| **Medium** | رفتار غلط در حالت‌های کم‌تکرار، پیام گمراه‌کننده | شمارنده‌ی اشتباه، بدون اثر مالی | تا یک هفته |
| **Low** | ظاهری، متن، عملکرد جزئی | تراز RTL | فهرست انتظار |

## 5) کاتالوگ الگوهای باگ (لنزهای عرضی)

هر بخش را «با این عینک‌ها» بخوانید. در پرامپت‌ها می‌توانید بنویسید: «لنز L7 و L9 را روی این فایل‌ها اعمال کن».

| لنز | الگو | پرسش کلیدی از AI | نشانه‌ی خطر در این کد |
|---|---|---|---|
| **L1** | رقابت (Race) / هم‌زمانی | «اگر دو درخواست هم‌زمان برسند چه می‌شود؟» | خواندن ← تصمیم ← نوشتن بدون `FOR UPDATE` یا UPDATE شرطی؛ `await` بین خواندن و نوشتن |
| **L2** | خودتوانی (Idempotency) | «اگر همین درخواست/وب‌هوک/کار صف دوباره بیاید؟» | کارهای صف با retry، بازگشت از درگاه، callback دوباره، دوبار کلیک |
| **L3** | مرز تراکنش | «آیا اثر بیرونی قبل از commit رخ می‌دهد؟» | ارسال پیامک/ایمیل/وب‌هوک داخل تراکنش؛ `afterCommit` فراموش‌شده |
| **L4** | ایزولاسیون مستأجر (Tenancy/IDOR) | «اگر `id` را با id فضای دیگر عوض کنم؟» | کوئری بدون `workspaceId`؛ مسیر `[id]` فقط با login؛ API با کلید فضای دیگر |
| **L5** | سطح دسترسی (RBAC) | «viewer یا member این عمل را می‌تواند؟» | server action بدون `can(role, perm)`؛ دکمه‌ی مخفی در UI ولی بدون بررسی سمت سرور |
| **L6** | ماشین حالت | «از هر وضعیت به هر وضعیت: کدام انتقال‌ها مجازند؟» | `UPDATE ... SET status` بدون `WHERE status IN (...)`؛ انتقال خارج از `lifecycle.ts` |
| **L7** | پول و گرد کردن | «مبلغ از کجا می‌آید؟ کلاینت؟ گرد می‌شود؟ مالیات؟» | اعتماد به مبلغ کلاینت؛ `Math.round` در جاهای ناهمسان؛ تخفیف/Proration منفی |
| **L8** | ورودی نامطمئن | «طول، نوع، ارقام فارسی، یونیکد، `null`، رشته‌ی خالی، آرایه به‌جای رشته؟» | `FormData` بدون Zod؛ `parseInt` روی ارقام فارسی؛ ورودی خیلی بلند |
| **L9** | نشت اطلاعات | «پیام خطا/لاگ/پاسخ API چه چیز را بازتاب می‌دهد؟» | `error.message` خام به کاربر؛ لاگ کردن توکن/OTP/کلید؛ تفاوت پیام «کاربر نیست» و «رمز غلط» |
| **L10** | SSRF و مسیر فایل | «آدرس/نام فایل کاربر به کجا می‌رسد؟» | وب‌هوک مقصد، تأیید مالکیت دامنه وردپرس، لینک تصویر، zip، نام فایل آپلود |
| **L11** | زمان و منطقه‌ی زمانی | «UTC یا تهران؟ شمسی یا میلادی؟ مهلت و انقضا؟» | مقایسه‌ی تاریخ بدون منطقه؛ ۲۹ اسفند؛ تغییر ساعت؛ `new Date()` پراکنده به‌جای `lib/clock.ts` |
| **L12** | نویسه‌ی فارسی/RTL/Bidi | «ارقام، ي/ی، ك/ک، نیم‌فاصله، ترکیب لاتین+فارسی؟» | جستجو، تطبیق شماره موبایل، اسم فایل، PDF، قلم، شکستن خط |
| **L13** | خطای جزئی و پیامد | «اگر مرحله‌ی میانی fail شود، چه چیزی نصفه می‌ماند؟» | حلقه‌های بدون try/catch؛ `Promise.all` که یک خطا همه را می‌شکند؛ کار نیمه‌تمام در دیسک/DB |
| **L14** | منابع و محدودیت | «بزرگ‌ترین ورودی؟ ۱۰۰۰۰ ردیف؟ ۵۰ مگابایت؟» | بارگذاری کل فایل در حافظه؛ N+1؛ `SELECT *` بدون limit؛ نبود صفحه‌بندی |
| **L15** | کش و داده‌ی کهنه | «اگر داده عوض شود، کش/`revalidate` به‌روز می‌شود؟» | `ttl-cache`، کش وضعیت لایسنس، کش پلن‌ها، Next cache |
| **L16** | رازها و رمزنگاری | «کلید کجا ذخیره می‌شود؟ در لاگ؟ در پاسخ؟ مقایسه‌ی زمان‌ثابت؟» | `SESSION_SECRET` ضعیف، مقایسه‌ی ساده‌ی توکن، کلید در JSON خروجی |
| **L17** | هم‌خوانی اسکیما | «اسکیما = DDL = دیتابیس زنده؟» | تغییر `schema/*.ts` بدون `ddl.ts`؛ ستون جدید بدون مقدار پیش‌فرض برای ردیف‌های قدیمی؛ CHECK با `NOT VALID` |
| **L18** | پیکربندی محیطی | «اگر env نباشد/اشتباه باشد؟ build یا runtime؟» | `process.env` در زمان build؛ مقدار پیش‌فرض ناامن؛ `ALLOW_DEV_OTP=1` در production |
| **L19** | پیام‌های کاربر و بازیابی | «اگر شکست بخورد کاربر چه می‌بیند؟ راه برگشت دارد؟» | خطای عمومی «مشکلی پیش آمد»؛ دکمه‌ی دوبار؛ loading بی‌پایان |
| **L20** | کدِ مرده و مسیر فراموش‌شده | «کدام مسیر قدیمی هنوز صدا زده می‌شود؟» | route قدیمی `api/billing/callback` بدون gateway؛ سازگاری عقب‌رو |

(۱) پس از نصب موفق، آیا هر راهی هست که `/install` دوباره اجرا شود و مدیر دوم یا بازنویسی دیتابیس بسازد؟ (۲) اگر دو درخواست نصب هم‌زمان برسند چه می‌شود؟ (۳) آیا `INSTALL_KEY` مقایسه‌ی زمان‌ثابت دارد و در لاگ/پاسخ می‌آید؟ (۴) اگر نصب وسط راه (بعد از ساخت جدول، پیش از ساخت مدیر) قطع شود، آیا حالت نیمه‌نصب قابل بازیابی است یا سیستم قفل می‌شود؟ (۵) رشته‌ی اتصال دیتابیس ورودی کاربر چگونه اعتبارسنجی می‌شود (SSRF به شبکه‌ی داخلی/تزریق پارامتر)؟»

### S01 — دیتابیس: اسکیما، DDL، قیدها، ایندکس، تراکنش  `[P0]`

**فایل‌های هدف:** `src/db/schema/*.ts` (۲۴ فایل: identity، tenancy، contracts، negotiation، documents، collect، vault، merge، finance، billing، health، kyc، licensing، messengers، notifications، platform، security، shop، states، support، wallet، wordpress، chat، developer، ai)، `src/db/ddl.ts`, `src/db/index.ts`, `src/db/pool-config.ts`, `src/db/sealed-text.ts`, `src/lib/db-lock.ts`, `src/modules/install/schema-sql.ts`, `drizzle.config.json`, `scripts/gen-schema-sql.mjs`

**اجزای ریز:**
1. هم‌خوانی سه‌گانه: `schema/*.ts` ← `ddl.ts` (نصب‌کننده) ← `drizzle-kit push`.
2. قیدهای CHECK ماشین حالت (`schema/states.ts`) و سازگاری با دیتابیس قدیمی (`NOT VALID` + `VALIDATE`).
3. ایندکس‌ها: یکتا، جزئی (مثلاً طرح پیش‌فرض)، زمانی، trigram (جستجوی تیکت).
4. FK و `ON DELETE` (cascade/set null/restrict) و حذف حساب.
5. `afterCommit` و تراکنش‌های تودرتو؛ `db-lock.ts` (advisory lock) و زمان‌بندی قفل.
6. استخر اتصال (`pool-config.ts`)، timeout، `statement_timeout`، اتصال نشتی.
7. `sealed-text.ts`: رمزنگاری ستون‌های حساس.
8. ارتقای نسخه: داده‌ی قدیمی + ستون جدید.

**پرامپت‌ها:**
- **S01-P1 (هم‌خوانی):** «هر جدول در `src/db/schema/*.ts` را با خروجی `ddl.ts` مقایسه کن. جدول/ستون/ایندکس/CHECK/default که فقط در یکی از دو جا هست را فهرست کن. آیا نصب تازه با نصب ارتقایی (drizzle push روی دیتابیس قدیمی) به یک ساختار می‌رسند؟»
- **S01-P2 (ارتقا روی داده‌ی واقعی):** «برای هر ستون `NOT NULL` یا CHECK که بعداً اضافه شده، ببین ردیف‌های قدیمی (مقدار null/وضعیت ناشناخته) هنگام `ALTER`/`VALIDATE` شکست می‌خورند یا نه. یک نصب قدیمی با داده‌ی نمونه فرض کن و فهرست خطاهای مهاجرت را بنویس.»
- **S01-P3 (FK و حذف):** «برای هر FK، رفتار حذف را بخوان. حذف یک کاربر، یک فضای کاری، یک قرارداد، یک امضاکننده: چه چیز یتیم می‌ماند؟ چه چیز به‌اشتباه cascade می‌شود (مثلاً سند حقوقی/ممیزی/فاکتور که نباید حذف شود)؟»
- **S01-P4 (تراکنش و afterCommit):** «همه‌ی `db.transaction` را grep کن. در هر کدام: آیا `await` شبکه‌ای (fetch، SMTP، SMS، فایل) داخل تراکنش هست؟ آیا خطا در `afterCommit` بی‌صدا بلعیده می‌شود؟ آیا تراکنش تودرتو یا اتصال دوم داخل تراکنش باز می‌شود (بن‌بست استخر)؟»
- **S01-P5 (ایندکس و کارایی کوئری):** «کوئری‌های لیست و جستجو را بخوان (`contracts/service/user-list.ts`, `query.ts`, `fulltext.ts`, `workspace-search.ts`). کدام بدون ایندکس مناسب است؟ کدام `LIKE '%x%'` بدون trigram دارد؟ کدام بدون `LIMIT` است؟»
- **S01-P6 (رمزنگاری ستونی):** «`sealed-text.ts` و هر مکان که از آن استفاده می‌شود: الگوریتم، IV یکتا، احراز یکپارچگی (GCM tag)، تغییر کلید، و رفتار هنگام ناموفق بودن رمزگشایی.»

**آزمون‌های مرتبط:** `schema-upgrade-phase1.test.ts`, `transaction-atomicity.test.ts`, `tests/global-setup.ts`, `npm run db:check`.
**تست دستی:** `S01`.

## 8) ابزارهای خودکار مکمل هوش مصنوعی

هوش مصنوعی «می‌خواند». این ابزارها «اجرا می‌کنند». هر دو لازم‌اند.

| ابزار | فرمان | چه باگی می‌گیرد |
|---|---|---|
| Vitest (واحد و یکپارچه) | `npx vitest run` | رگرسیون منطق (۷۰+ فایل آزمون موجود) |
| تایپ‌اسکریپت | `npx next typegen && npm exec tsc -- --noEmit --pretty false` | ناسازگاری نوع |
| بیلد | `npm run build` | خطای SSR، مسیر ناقص |
| ESLint | `npx eslint src tests --quiet` | الگوهای خطرناک، hook اشتباه |
| E2E Playwright | `npm run test:e2e` | جریان‌های کاربر (۱۳ سناریو) |
| QA چندلایه | `npm run qa` (`qa:smoke`, `qa:contract`, `qa:a11y`, `qa:perf`, `qa:lighthouse`, `qa:visual`, `qa:security`, `qa:load`) | دود، قرارداد API، دسترس‌پذیری، سئو، بصری، امنیت، بار |
| اسکیما | `npm run db:check` | ناهماهنگی `schema` ↔ DDL |
| دود روی سرور | `node scripts/smoke.mjs https://دامنه` | هدرهای امنیتی، صفحه‌های عمومی، ۴۰۱ APIها |
| افزونه‌ی وردپرس | `php tests/php/run.php`, `npm run plugin:verify`, `php -l` | سینتکس PHP، یکپارچگی انتشار |
| زیرساخت | `npm run infra:check`, `infra:selftest` | Docker/Caddy/اسکریپت‌ها |
| وابستگی‌ها | `npm audit --omit=dev` | CVE |
| اسکن راز | `gitleaks detect` یا `trufflehog` (روی کل تاریخچه‌ی git) | کلید/رمز در کد و تاریخچه |
| تحلیل ایستا | `semgrep --config p/owasp-top-ten --config p/typescript --config p/php` | الگوهای OWASP |
| کد مرده | `npx knip` | مسیر فراموش‌شده (L20) |
| بیدی/RTL | آزمون‌های `unit/bidi-text.test.ts` | چینش متن |
| سنجش حافظه | `node --inspect` + `qa:load` | نشت و پیک حافظه |
| شبیه‌ساز | `npx tsx simulator/cli.ts` | قطعی/کندی/خطای سرویس‌های بیرونی |
| ZAP/Nuclei | روی نمونه‌ی staging (نه production) | آسیب‌پذیری‌های وب |
| PHP | `phpcs` با استاندارد WordPress-Security و Plugin Check | امنیت افزونه |
| اسکریپت شل | `shellcheck scripts/*.sh`, `hadolint Dockerfile` | اشتباهات اسکریپت و Docker |

**قانون:** هر یافته‌ی هوش مصنوعی که با ابزار قابل‌اثبات است، **باید** با ابزار اثبات شود.

## 9) دفتر پیگیری پیشرفت

یک فایل جدا (مثلاً `docs/BUG-HUNT-LEDGER.md` که بعداً خودتان می‌سازید یا یک Google Sheet) با این جدول‌ها:

### الف) پیشرفت بخش‌ها
| بخش | نشست‌ها | شکارچی ✔ | دادستان معکوس ✔ | یافته‌ها (C/H/M/L) | رفع‌شده | آزمون افزوده | تست دستی ✔ | وضعیت |
|---|---|---|---|---|---|---|---|---|
| S00 | | | | | | | | ☐ |
| S01 | | | | | | | | ☐ |
| … | | | | | | | | ☐ |
| S26 | | | | | | | | ☐ |
| X1…X12 | | | | | | | | ☐ |

### ب) ثبت یافته‌ها
| شناسه | شدت | بخش | عنوان | commit کشف | وضعیت (جدید/رد/تأیید/رفع/بسته) | commit رفع | آزمون | یادداشت |
|---|---|---|---|---|---|---|---|---|

### پ) رد شده‌ها (دانش ارزشمند)
هر یافته‌ی ردشده را با دلیل بنویسید تا نشست‌های بعدی دوباره ادعایش نکنند.

## 10) معیار «تمام شد» و دروازه‌ی لانچ

لانچ **فقط** وقتی مجاز است که همه‌ی این‌ها درست باشد:

### دروازه‌ی کد
- [ ] همه‌ی بخش‌های موج A تا D (S00–S15) و S23: هر دو نشست (شکارچی و دادستان) انجام شده.
- [ ] صفر یافته‌ی Critical و صفر High باز. Mediumها یا رفع شده‌اند یا با دلیل پذیرفته شده‌اند.
- [ ] برای هر باگ Critical/High رفع‌شده، آزمون خودکار در `tests/` هست.
- [ ] جاروب‌های X1، X7، X11 انجام شده.
- [ ] `npx vitest run` سبز، `tsc` بدون خطا، `npm run build` موفق، ESLint بدون خطا، `npm run db:check` سبز، `npm run qa` سبز.
- [ ] `npm audit --omit=dev` بدون آسیب‌پذیری High/Critical قابل‌بهره‌برداری.
- [ ] `gitleaks` بدون راز واقعی در تاریخچه‌ی git.

### دروازه‌ی عملیات
- [ ] `MANUAL-QA-CHECKLIST.md`: همه‌ی بندهای علامت **[P0]** تیک خورده، و هیچ شکست باز نیست.
- [ ] بک‌آپ و بازیابی روی سرور جدید با موفقیت تمرین شده.
- [ ] یک قرارداد واقعی کامل (صدور ← OTP واقعی ← امضای دو نفر ← PDF ← استعلام) و یک پرداخت واقعی (با مبلغ کم و بازپرداخت) انجام شده.
- [ ] داشبورد سلامت (`/platform/health`) امتیاز آمادگی لانچ کامل (همه سبز) در سرور اصلی.

### قانون توقف
اگر در یک بخش، ۳ نشست پشت‌سرهم یافته‌ی **تازه‌ی** Critical/High پیدا شد، آن بخش «بی‌ثبات» است: تمام آن را با یک نشست «خواندن خط‌به‌خط» دوباره بررسی کنید و ببینید آیا مشکل ساختاری (نه نقطه‌ای) هست.
